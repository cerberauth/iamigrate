This guide covers moving users from Azure AD B2C to Auth0: what carries over and what doesn't, how their passwords and second factors are handled, and the commands to run. It sticks to what is specific to this pair. The [export guide for Azure AD B2C](../../export/azure-ad-b2c/) and the [import guide for Auth0](../../import/auth0/) cover each side in full, including a rehearsal with synthetic users.

## What carries over

| | Azure AD B2C to Auth0 |
| --- | --- |
| **Passwords** | Not carried over: B2C never returns hashes. Users reset their password, or you check passwords against B2C at sign-in. |
| **Second factors** | Not exported: users enroll again on Auth0. |
| **User IDs** | The Azure AD object ID is kept as `source_id`, and Auth0 adds its connection prefix to it. |

The Azure AD B2C export leaves behind:

- Password hashes (Microsoft Graph never returns them)
- MFA enrollments
- Links to federated identity providers (the issuer and ID are kept in `app_metadata.federated_identities`, nothing more)
- Groups, directory roles and application role assignments
- Custom policies and user flows
- Timestamps

## Before you start

- iamigrate installed (see [Installation](../../../installation/)).
- An app registration in the B2C tenant with the Microsoft Graph **application** permission `User.Read.All`, admin consent granted, and a client secret.
- The names of any custom attributes you want to export, in the form `extension_<app ID>_<name>`.
- **Auth0.** An Auth0 tenant (**use a development tenant for the rehearsal**), a database connection to import into, the MFA factors you intend to import enabled under **Security → Multi-factor Auth**, and Management API credentials. The [import guide](../../import/auth0/#1-prepare-the-auth0-tenant) walks through it.

<Aside type="caution">
  The export contains personal data. Write it somewhere access-controlled, and delete it once the migration is done.
</Aside>

## 1. Export from Azure AD B2C

```sh
export AZURE_TENANT_ID=your-tenant.onmicrosoft.com   # the B2C tenant's domain or directory ID
export AZURE_CLIENT_ID=...       # the app registration's Application (client) ID
export AZURE_CLIENT_SECRET=...   # and its client secret

iamigrate export --source azure-ad-b2c \
  --filter "creationType eq 'LocalAccount'" \
  --out ./export/
```

The `--filter` above leaves out the tenant's administrators and guests. Add `--extension-attributes` to export custom attributes into `user_metadata`, and `--limit` to try the export on a sample first.

The export is a snapshot: users created, and passwords changed, after it aren't in it, so plan a freeze or a final re-export before cutover. Check `export/manifest.json` for `skipped_records`, because the command exits with status `0` even when users are skipped.

## 2. Deal with passwords

Azure AD B2C never returns password hashes, so users are created in Auth0 without a password. The way to avoid asking everyone to reset it is to check each password against B2C as users sign in. In Auth0, that means a custom database login script that checks each password against B2C as users sign in ([Auth0 custom database docs](https://auth0.com/docs/authenticate/database-connections/custom-db)). iamigrate doesn't do that part itself, since it runs inside Auth0. The approach, including how to decide when to stop, is in [Migrating from Azure AD B2C without password export](https://www.cerberauth.com/blog/migrating-from-azure-b2c-without-password-export/).

Whatever you choose, the users who haven't signed in by cutover need to set a new password. Send them a password reset email, or let them use **Forgot password** at first login.

## 3. Fit the data to Auth0

- **Email is required.** Auth0's bulk import needs an email, so a user without one isn't sent and is reported as `TRANSLATION_ERROR`. B2C users who sign in with a username or a phone number have no email, and a user with no email, username or phone number is skipped by the export.
- **Metadata.** Custom attributes you ask for land in `user_metadata`, and each federated sign-in identity in `app_metadata.federated_identities`. Auth0 takes `app_metadata` and `user_metadata` as they are, and `validate` reports a top-level `app_metadata` key Auth0 reserves, such as `email` or `blocked`.
- **Verified flags.** B2C doesn't say whether an address is verified, so every email and phone number is exported as unverified, and Auth0 stores `email_verified: false`.

## 4. Validate against Auth0

Set the target in the scaffolded mapping, then check the export against what the target can import. `validate` makes no network calls:

```sh
iamigrate map --target auth0 --mapping ./export/mapping.yaml --connection-id con_XXXXXXXXXXXXXXXX
iamigrate validate --in ./export/users.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml --target auth0
```

Add `--connection-config connection.json` (a `GET /connections/{id}` response) to check usernames against the connection's own rules.

Fix every reported problem at the source, or in the CMF records, and run it again until it comes back clean. Review `mapping.yaml` too: custom metadata keys are flagged under `manual_steps` for you to place, rather than guessed at.

## 5. Rehearse, then import

Do a rehearsal first. Follow the [Auth0 import guide](../../import/auth0/) with a small fixture, against a disposable target, and sign in as a few of the users (see [Generate test fixtures](../../generate-test-fixtures/)).

For the real run, point iamigrate at Auth0:

```sh
export AUTH0_DOMAIN=your-tenant.us.auth0.com
export AUTH0_CLIENT_ID=...       # a Machine-to-Machine application with the scopes the import guide lists
export AUTH0_CLIENT_SECRET=...
```

Split off a small canary, import it, and check the result before you import the rest:

```sh
gunzip -c export/users.cmf.jsonl.gz | head -n 100 | gzip > export/canary.cmf.jsonl.gz
gunzip -c export/users.cmf.jsonl.gz | tail -n +101 | gzip > export/rest.cmf.jsonl.gz

iamigrate import auth0 \
  --in ./export/canary.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml \
  --connection-id con_XXXXXXXXXXXXXXXX \
  --report ./export/canary-report.json
```

Sign in as a few canary users, then import the rest:

```sh
iamigrate import auth0 \
  --in ./export/rest.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml \
  --connection-id con_XXXXXXXXXXXXXXXX \
  --report ./export/rest-report.json
```

The command exits with status `0` even when users fail. Always read the reports: each failed user is listed under `failed` with a code, and the follow-up lists (`requires_password_reset`, `requires_reenrollment` and so on) say who needs to hear from you. The [import guide](../../import/auth0/) explains each code.

## 6. Verify

Reconcile the file with the live target. It reports users missing from it and drift in the fields it can read back:

```sh
iamigrate diff auth0 --in ./export/users.cmf.jsonl.gz --mapping ./export/mapping.yaml
```

There is no password to prove here, so check the reset path instead: make sure a test user can set a new password on Auth0 and sign in.

Auth0 builds the `user_id` as `auth0|<source_id>`, so the Azure AD object ID `3f2b9c1e-…` becomes `auth0|3f2b9c1e-…`. If your applications reference users by the old ID, keep that mapping.

## Cutover

- Freeze changes in Azure AD B2C, re-export, and import the final file.
- Reconnect what the export doesn't carry: the federated identity providers (the issuer and ID of each are in `app_metadata.federated_identities`), groups and roles (Auth0 can take them from files you write, see [Organizations, roles and groups](../#organizations-roles-and-groups)). Then point every application at Auth0.
- Tell users what to expect. They need to set a new password, unless you check passwords against B2C as they sign in. Second factors aren't exported, so users enroll them again.
- Clean up the rehearsal. Delete the rehearsal users from **User Management → Users**, or delete the connection and recreate it, before you import real ones. Users deleted any other way can linger in Auth0's user store and cause `DUPLICATED_USER` later.
