This guide covers moving users from Firebase to Ory Kratos: what carries over and what doesn't, how their passwords and second factors are handled, and the commands to run. It sticks to what is specific to this pair. The [export guide for Firebase](../../export/firebase/) and the [import guide for Ory Kratos](../../import/kratos/) cover each side in full, including a rehearsal with synthetic users.

## What carries over

| | Firebase to Ory Kratos |
| --- | --- |
| **Passwords** | Not carried over: only Firebase can verify its modified scrypt. Users reset their password. |
| **Second factors** | Not carried over: users enroll again on Ory Kratos. |
| **User IDs** | Ory Kratos generates new IDs. The report's `target_ids` maps each `source_id` to its new one. |

The Firebase export leaves behind:

- Linked sign-in providers (only the email and phone number they carry are kept)
- Timestamps
- Tenants (only the project's default tenant is read)
- Anonymous and custom-token users, which the export skips

## Before you start

- iamigrate installed (see [Installation](../../../installation/)).
- A Google service account key for the project, with a role that can list users such as **Firebase Authentication Admin**, or an OAuth2 access token.
- **Ory Kratos.** A self-hosted Kratos instance whose **Admin API** you can reach, with an identity schema that accepts the traits iamigrate writes and the `password` method enabled (**use a disposable instance for the rehearsal**). The [import guide](../../import/kratos/#1-prepare-the-kratos-instance) walks through it.

<Aside type="caution">
  The export contains password hashes and personal data. Write it somewhere access-controlled, never commit it, and delete it once the migration is done.
</Aside>

## 1. Export from Firebase

```sh
export FIREBASE_PROJECT_ID=acme-prod
export GOOGLE_APPLICATION_CREDENTIALS=./service-account.json

iamigrate export --source firebase --out ./export/
```

The export is a snapshot: users created, and passwords changed, after it aren't in it, so plan a freeze or a final re-export before cutover. Check `export/manifest.json` for `skipped_records`, because the command exits with status `0` even when users are skipped, and for the per-algorithm counts.

## 2. Deal with passwords

Firebase hashes passwords with a modified scrypt that depends on two secrets shared by the whole project, and only Firebase can verify it. Ory Kratos doesn't take scrypt, so `validate` reports those users as `unsupported by target`. Passwords can't be carried over, whatever you pass to the export.

That makes the project's hash parameters pointless for this move, so you can skip step 2 of the [Firebase export guide](../../export/firebase/#2-get-the-password-hash-parameters). Drop every password from the export, so the users are created without one:

```sh
gunzip -c export/users.cmf.jsonl.gz \
  | jq -c '.password = null' \
  | gzip > export/users.ready.cmf.jsonl.gz
```

Users who only sign in with Google, Apple or a phone number have no password to lose. The others need to set a new password. Let them use Kratos' recovery flow. The minimal identity schema in the import guide enables recovery by email.

Read the later steps from `export/users.ready.cmf.jsonl.gz`.

## 3. Deal with second factors

| Second factor in the export | On Ory Kratos |
| --- | --- |
| SMS (portable unless Firebase returned the number masked) | Not imported. The user is created and listed under `requires_reenrollment`, and enrolls again after signing in. |
| TOTP (flagged non-portable: Firebase never returns the secret) | Not imported. The user is created and listed in the report for follow-up, and enrolls again after signing in. |

## 4. Fit the data to Ory Kratos

- **The identity schema decides what imports.** Kratos rejects any identity that doesn't match it. The schema needs an `email` trait marked as a password identifier (or `username`/`phone`, if that's how your users sign in) and must not require traits iamigrate doesn't fill. Run `validate` with `--schema-file` to find mismatches before the import.
- **`app_metadata`** goes to `metadata_admin`, where it isn't visible to the user.
- **Phone numbers.** The first one becomes the `phone` trait, so declare it in the schema, as `"format": "tel"` if you want it checked. Kratos validates it as E.164.
- **Names aren't imported.** Kratos gets no `given_name`, `family_name` or `name`. To keep them, add them to `user_metadata` under the trait names your schema expects, with a [`metadata` route in `mapping.yaml`](../../../reference/mapping/#metadata) or by editing the CMF records.

## 5. Validate against Ory Kratos

Set the target in the scaffolded mapping, then check the export against what the target can import. `validate` makes no network calls:

```sh
iamigrate map --target kratos --mapping ./export/mapping.yaml
iamigrate validate --in ./export/users.ready.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml --target kratos --schema-file identity.schema.json
```

`--schema-file` checks every user's traits against your identity schema, so schema problems show up before the import.

Fix every reported problem at the source, or in the CMF records, and run it again until it comes back clean. Review `mapping.yaml` too: custom metadata keys are flagged under `manual_steps` for you to place, rather than guessed at.

## 6. Rehearse, then import

Do a rehearsal first. Follow the [Ory Kratos import guide](../../import/kratos/) with a fixture that holds the same hash algorithms and second factors as your users, against a disposable target, and sign in as a few of the users (see [Generate test fixtures](../../generate-test-fixtures/)).

For the real run, point iamigrate at Ory Kratos:

```sh
export KRATOS_ADMIN_URL=http://127.0.0.1:4434
```

Split off a small canary, import it, and check the result before you import the rest:

```sh
gunzip -c export/users.ready.cmf.jsonl.gz | head -n 100 | gzip > export/canary.cmf.jsonl.gz
gunzip -c export/users.ready.cmf.jsonl.gz | tail -n +101 | gzip > export/rest.cmf.jsonl.gz

iamigrate import kratos \
  --in ./export/canary.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml \
  --schema-id default \
  --report ./export/canary-report.json
```

Sign in as a few canary users, then import the rest:

```sh
iamigrate import kratos \
  --in ./export/rest.cmf.jsonl.gz \
  --mapping ./export/mapping.yaml \
  --schema-id default \
  --report ./export/rest-report.json
```

The command exits with status `0` even when users fail. Always read the reports: each failed user is listed under `failed` with a code, and the follow-up lists (`requires_password_reset`, `requires_reenrollment` and so on) say who needs to hear from you. The [import guide](../../import/kratos/) explains each code.

## 7. Verify

Reconcile the file with the live target. It reports users missing from it and drift in the fields it can read back:

```sh
iamigrate diff kratos --in ./export/users.ready.cmf.jsonl.gz --mapping ./export/mapping.yaml
```

There is no password to prove here, so check the reset path instead: make sure a test user can set a new password on Ory Kratos and sign in.

Kratos generates each identity's UUID and rejects a chosen one. The report's `target_ids` maps every `source_id` to it. If your applications reference users by the old ID, keep that mapping.

## Cutover

- Freeze changes in Firebase, re-export, and import the final file.
- Reconnect what the export doesn't carry: the linked sign-in providers such as Google or Apple, which users have to link again. Then point every application at Ory Kratos.
- Tell users what to expect. They need to set a new password. A second factor that didn't move has to be enrolled again.
- Clean up the rehearsal. Delete the rehearsal identities with [`rollback kratos`](../../../reference/cli/rollback-kratos/), or throw the disposable instance away.
